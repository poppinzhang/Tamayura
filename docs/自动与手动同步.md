# 自动与手动同步

## 规则

相册同步更新对端媒体元数据和缩略图，原文件仍在点击媒体后按需下载。所有平台使用同一个 Flutter `AppController` 和设置界面；当前 Android、macOS、Windows 实现遵循相同规则。

- 自动同步按设备分别计时，默认间隔为 12 小时。没有同步记录的新设备可立即尝试；已有设备只有到达「最近一次同步尝试开始时间 + 设置的间隔」才可再次自动尝试。
- 自动和手动尝试共用 `peers.last_sync`。成功、目录未变化、连接失败、身份校验失败和目录接收失败都计时，不因失败立即自动重试。时间写入数据库，退出或重启应用不会重置间隔。
- 设备页面为每台已记住的设备显示「最后成功同步：YYYY-MM-DD HH:mm:ss」，使用查看设备的本地时区。没有成功记录时显示「最后成功同步：尚未成功同步」；离线、同步中和失败时继续显示上次成功时间。
- 成功时间独立保存在 `peers.last_successful_sync`，以本机完成相册同步的时间为准。完整目录（包括空目录）提交成功、对端确认目录未变化都更新；发现设备、核验在线状态、收到部分媒体或下载原文件不更新。失败重试仍按尝试时间计算自动同步间隔，不会覆盖成功时间。
- 右上角刷新按钮立即手动同步已记住的设备，不受间隔限制。桌面刷新快捷键、明确点击「继续同步 / 重试」、输入 IP 或扫码连接也属于用户主动尝试，使用同一计时规则。
- 相册与设备页面不提供下拉同步，滚动和下拉手势仅用于浏览。
- 「设置 → 自动同步间隔」可填写 1–8760 的整数小时，默认 12。设置持久保存；保存失败保留原值并提示重试。调整间隔以原来的最近尝试时间重新计算，缩短后已到期的设备可立即尝试，延长后等待新的截止时间。

例如 09:00 自动同步失败，默认下次自动尝试不早于 21:00。如果 15:00 点击刷新，无论这次成功还是失败，下次自动尝试都不早于次日 03:00。

## 实现

启动、返回前台、mDNS / DNS-SD 发现事件和定时器都经过同一间隔判断。同一设备正在同步时合并重复触发；排队的新地址也重新检查间隔，不因旧地址失败立即再同步。

控制器在已知设备的第一次网络操作之前保存尝试时间，客户端构造异常和身份请求失败也被计入。首次手动连接尚不知道设备 ID 时，身份解析后按真实 ID 合并并记录；无法识别的地址保留手动重试入口，不创建空 ID 设备。手动输入已记住的地址仍允许识别使用该地址的新设备。同步开始后被生命周期中止仍保留已经写入的时间和可恢复断点。

`Peer` / `DeviceView` 分别保留 `lastSync`（尝试开始）和 `lastSuccessfulSync`（成功完成）。只有控制器显式 `upsertPeer` 写入非空 `lastSync` 才更新尝试计时；目录层不允许旧 `Peer` 的尝试时间覆盖新记录。

`markPeerSynced`、完整快照提交和测试用快照替换，在成功事务内写入本机当前成功时间；目录写入失败时整个事务回滚。普通 `upsertPeer` 不写成功时间，防止发现广播、旧身份对象或进行中的尝试清除、覆盖成功记录。控制器刷新缓存时从数据库读取成功时间，并在地址更新和同步状态切换时保留显示值；重启后从设备记录恢复。

媒体库 schema 升至 6，新增可空的 `last_successful_sync` 列。按 v1.0.0 前策略直接重建旧媒体库，不提供迁移：设置、记住的设备、离线相册、缩略图和下载历史索引清空，需要重新选择目录并发现设备。外部原始媒体、已保存的接收文件和独立下载任务库不受这次 schema 调整影响。

设备在线探测与相册同步独立。未到同步时间时，重新发现设备仍可核验身份、更新 IP、名称和在线状态，以便下载使用最新地址；这类身份请求不拉取目录、缩略图，也不重置同步计时。同地址且已经在线的重复广播直接忽略。自动发现中缺少设备 ID 的无效事件不会发起同步。

控制器只为最近到期的设备安排一个计时器，每次尝试或修改设置后重新计算。停止共享网络、销毁控制器时取消；恢复运行后从持久化时间重新判断。定时检查沿用每批最多三台记住设备的同步方式，同一设备不会并发接收两个相册快照。

## 范围与限制

计时器依赖应用进程运行和系统允许执行，不新增后台常驻或唤醒服务。Android 沿用已有后台共享服务；桌面需要应用运行、系统清醒。系统暂停期间不会保证准时执行，恢复后再判断是否到期；网络不可用时的一次失败同样等待完整间隔，用户可随时手动刷新。

本次调整接收端相册同步的频率。本机共享目录的扫描仍沿用现有规则：手动刷新和目录增删主动扫描，返回前台按本地扫描间隔处理，供其它设备读取；原文件下载及其断线重试不受相册自动同步间隔影响。
