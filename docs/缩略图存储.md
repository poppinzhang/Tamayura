# 缩略图存储与目录同步

本文描述接收端的持久离线缓存。当前未发布源码另在 Windows 来源端增加有容量上限的内存缓存，复用 RAW 预览生成结果；两者的生命周期和用途不同，见 [Windows RAW 预览与来源端缓存](Windows缩略图.md)。

## 为什么独立保存缩略图

媒体库 schema 5 将缩略图放入独立的 `thumbnails` 表，正式相册 `media` 和同步暂存 `sync_media` 只保存 `thumbnail_id`。目录新增或删除文件时，仍完整核对分页元数据，但不会再把所有未变缩略图复制进暂存表。

新图片的字节只插入一次。首次同步提交、断点恢复、目录 revision 变化后的复用，都只调整元数据和缩略图引用。这里不进行图片内容哈希去重，也不维护引用计数；两个不同的媒体文件可以各有一条内容相同的缩略图记录。

## 表结构与就绪状态

- `thumbnails(id INTEGER PRIMARY KEY, bytes BLOB NOT NULL)` 保存不可变缩略图字节。
- `media.thumbnail_id` 为非空外键，正式相册只包含已完成缩略图请求的媒体。
- `sync_media.thumbnail_id` 为可空外键：`NULL` 表示尚未取得缩略图；非空表示已经完成。
- 空字节缩略图也是已完成请求，具有独立 ID。单张媒体没有可用预览时可以显示占位图，不会因为空 BLOB 被重复请求或永远阻塞提交。
- 两张引用表都为 `thumbnail_id` 建立索引，供无引用数据清理使用。

每次收到缩略图，在同一个事务中插入字节、更新对应暂存行。覆盖暂存结果会创建新记录，不原地修改共享字节；旧记录只有不再被任何条目引用时才删除。无效媒体 ID、失效的会话或事务失败不会留下半写入的缩略图。

## 同步、预览与提交

`stageMediaPage` 继续按完整元数据匹配正式相册和未完成快照；匹配成功仅复用 ID，未匹配项等待网络响应。只有元数据完全匹配时才复用，名称、大小、修改时间、共享根或相对路径变化仍会重新取得缩略图。

相册预览将已就绪的暂存项覆盖到正式相册上，分页与合集聚合只操作轻量字段。真正显示当前页或合集封面时再按 ID 读取 BLOB，不在组合关系中装入整个图片库。未完成同步依然保留旧相册，删除只有在完整快照提交后才生效。

`commitPeerSnapshot` 在单个事务中校验数量与就绪状态、发布新增/变更、删除对端已移除项、递增 generation、移除该设备已失效的会话并清理无引用缩略图。提交无需从暂存表重新写一遍图片字节。原有 `base_generation` 校验与会话接管继续阻止迟到请求、旧同步提交覆盖新状态。

## 回收规则

提交、主动中止、完整替换相册和覆盖暂存缩略图后，只删除同时不被 `media` 和任何 `sync_media` 引用的记录。引用更新与回收在同一事务内完成。

不能随会话删除直接级联删除图片：其他会话或正式相册可能仍使用同一 ID。尚可恢复的同步断点会保留自己的引用；打开第二个引擎连接不会清除它们。删除一台设备的相册不会清除另一台设备仍使用的数据。

SQLite 删除记录后会把页面留给后续写入复用，数据库文件通常不会立即缩小。本实现消除了重复 BLOB 写入，不在每轮同步运行 `VACUUM`。仍会写入全量轻量元数据，因而新增一张图的总写入量不等于这一张图的大小；没有新增增量同步协议。

## 数据库重建

按 v1.0.0 前策略，媒体库从旧 schema 升到 5 时直接清空重建，不迁移旧表。需要重新选择共享与接收目录、发现设备并建立相册缓存；媒体库中的旧设置、设备、下载历史索引和同步断点会清空。外部原始媒体、已保存到接收目录的文件不会删除，独立下载任务库不由这次媒体库 schema 升级重建。

## 验证

`test/thumbnail_storage_test.dart` 覆盖首次提交和重启保持同一图片引用、空图就绪、跨 revision 复用、多会话共享与回收、覆盖时图片不可变、失败/迟到请求不泄漏、清理时隔离其他设备，以及 5000 张每张 20 KiB 的图片库仅新增一张的回归场景。

性能回归检查全部 5000 张旧图复用相同 ID，暂存不新增任何旧图片记录，提交只增加新图片记录；同时检查数据库页面增长远小于全量图片约 98 MiB。阈值为 8 MiB，给元数据和索引布局留出余量，不依赖某一 SQLite 版本的精确 WAL 文件大小。

原有 `test/database_test.dart` 与 `test/catalog_restart_test.dart` 继续覆盖渐进预览、分页、合集封面、断点接管、多连接和双方进程重启后的同步恢复。
