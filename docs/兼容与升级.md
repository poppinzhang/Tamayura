# 正式版本兼容与升级

从 v1.0.0 起，正式版本按语义化版本管理：补丁版本修复问题，次版本增加兼容功能；需要破坏既有数据、配置或协议契约的变更必须评估主版本升级、过渡路径和用户影响，不能通过提高版本号绕过数据保护和发布验证。

## v1.0.0 基线

| 持久化或通信范围 | 基线 |
| --- | --- |
| 相册、设备、设置、已保存文件登记和同步断点 | `tamayura.db`，SQLite schema 7 |
| 下载任务、分片进度与接收目录名称分配 | `tamayura_transfers.db`，SQLite schema 3 |
| 设备身份与媒体传输 | `proto/media.proto`，`mediaProtocolVersion = 4` |
| 配置 | 相册数据库 `settings` 中的现有键与值格式，以及当前原生平台保存的目录授权和设置 |

本次发布保留现有 schema 和协议编号。已使用这两种 schema 的安装可以直接打开原数据库，设置、已记忆设备、离线相册、下载登记、同步断点和下载任务均不因版本号变为 v1.0.0 而重建。0.x 历史格式不纳入正式版兼容承诺，不补建旧版迁移路径；版本号相同不代表数据库内容已通过损坏检查。

## 数据保护

两个数据库都显式拒绝不受支持的 schema 升级与降级。版本不匹配时打开失败，界面显示三语错误提示，数据库内容和 schema 版本保持原状；不会删除表、将旧格式标成新格式或悄悄创建替代数据库。初始化在下载调度和分片清理之前停止，不会借启动失败清理下载分片或已保存文件。

遇到该错误应保留数据库与下载暂存，使用支持原数据格式的应用版本，或等待提供相应迁移的版本。卸载、清空应用数据和重建数据库不能作为正式版的默认升级流程。当前没有提供数据库降级转换工具。

后续 schema 变更必须随功能提供明确、事务性的升级迁移，保留用户配置、设备、下载登记与未完成任务，并验证既有正式版数据升级、迁移失败回滚、重复打开及不支持版本拒绝路径。迁移涉及外部文件时，必须设计中断恢复和失败处理，不能把 SQLite 事务当作跨文件系统事务。本次不添加尚无实际格式变更的迁移框架。

## 配置与协议

后续配置格式变更须保留正式版用户选择并提供有测试的转换；无效值的读取兜底不得被扩展为静默覆盖、删除有效旧配置。平台目录授权失效仍按原有错误处理和重新授权流程处理。

v1.0.0 继续通过身份握手核对协议 4；不兼容对端在导入元数据前被拒绝。协议新增应优先使用兼容的 protobuf 字段与 RPC 演进，不能改用或复用已有字段编号及改变既有字段含义。未来需要协议编号变化时，须明确正式版本间支持范围、过渡策略与不兼容提示，并同时测试新旧受支持端的客户端、服务端及失败行为。应用版本和协议版本独立，兼容的补丁或次版本不应仅因应用版本变化而互相拒绝。

## 验证入口

`test/database_compatibility_test.dart` 验证两种基线 schema 的无损重开、不受支持的升级与降级拒绝、表结构和所有记录保留，以及数据库打开失败时的可见错误和分片保护。现有 `test/network_test.dart` 继续验证协议不兼容时在导入目录前失败。配置、下载、同步与平台权限行为同时由各自回归测试覆盖；具体执行结果记录在对应发布记录，不能以本文说明替代当次测试。
