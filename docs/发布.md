# 发布与打包

当前源码统一版本为 **0.7.0+11**。Android、macOS 和 Windows 均从根目录 `pubspec.yaml` 读取版本：Android versionName `0.7.0` / versionCode `11`，macOS CFBundleShortVersionString `0.7.0` / CFBundleVersion `11`，Windows 数字文件版本 `0.7.0.11`。0.7.0 正在准备发布，本轮完整测试、打包和远端发布尚待完成，实际进度见 [0.7.0 发布记录](releases/0.7.0.md)。

0.6.1 已完成测试、打包和自动核验，并发布为 [GitHub Pre-release](https://github.com/poppinzhang/Tamayura/releases/tag/v0.6.1)。实际执行结果见 [0.6.1 发布记录](releases/0.6.1.md)。0.6.0 的 Tag 发布尝试因 Android SDK 初始化失败而未生成 Release，原 Tag 保留，详见 [0.6.0 记录](releases/0.6.0.md)。当前发布目标包括 Android 通用 APK、macOS Universal ZIP 和 Windows x64 ZIP；三个平台的可执行产物全部构建、验证后，才可标记全平台交付完成。Windows 源码交接 ZIP 只是构建输入，不能代替 Windows 可执行包。历史本地试用包与对应版本记录保留原样，不视为本次源码的验证结果。

## 版本与发布记录

1. 日常改动记在 `CHANGELOG.md` 的 `## unstaged`，分类记录功能、改进、修复和限制。
2. 发布时更新 `pubspec.yaml` 的版本和递增构建号，三个平台共用该版本；不要沿用已发布版本号打包新源码。
3. 将本次变更放入 `## <版本号>`，记录真实日期、交付状态和已知限制，前面保留空的 `## unstaged`。
4. 按需同步英文和中文 README、新增 `docs/releases/<版本号>.md`；构建仍在等待时明确写“待构建”，不将源码检查、历史结果或未执行的 CI 写成通过。
5. 本地打包产物与核验记录保留在本地 `dist/<版本号>/`；CI 在自己的产物目录生成平台包、独立校验和、联合 `SHA256SUMS` 和 `release.json`，并完成版本、字节数及 SHA-256 自动核验。本地与 CI 产物分别留存，不要求把最终 CI 包下载到本地。执行顺序以下文“每次发布的固定顺序”为准，本节不是提前创建 Tag 的依据。

发布文档、验证记录、日志和产物说明不得记录开发、打包或测试环境的内网地址、机器名、登录账号、SSH 连接信息、个人目录路径、密钥及凭据；只保留必要的通用工具链要求和脱敏结果。临时执行日志不得直接复制为公开发布记录。编译器可能把源码绝对路径写入可执行文件；发行包应从不含个人信息的通用临时源码目录构建，完成后扫描归档及解压内容中的环境隐私标记，再生成最终校验和。

既有版本记录中的交付方式为本地试用包。当前源码增加下述 GitHub Tag 自动发布流程；配置存在不代表已经远端运行或上传。本地生成安装包不等于已经上传。试用包需全部适用的自动化检查通过，并记录未完成的真机验收。正式公开发布前还需真实跨设备验收、干净环境重建，以及平台要求的公开分发签名。

## GitHub Tag 自动发布

`.github/workflows/release.yml` 在推送 `v*` Tag 时启动，只接受严格的 `v主版本.次版本.修订号`，例如 `v0.6.0`。日常 Android、macOS、Windows 工作流继续处理分支推送、Pull Request 和手动检查，不再因 Tag 重复构建。发布流程始终使用 Flutter 3.47.6 stable / Dart 3.13.5，三个平台均按锁文件解析依赖。

### 首次配置 Android 签名

在目标仓库的 **Settings → Secrets and variables → Actions → Repository secrets** 中添加以下四项。使用当前 `android/key.properties` 指定的专用 release 密钥，使 CI 与本地后续构建采用同一签名；不要为了 CI 重新生成不同的密钥。0.6.1 使用已切换的个人证书，与既有 0.5.0 及更早安装包不同，安装影响见下文 Android 签名说明。

| Secret | 内容 |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | release keystore 文件的 Base64 内容；Base64 只是编码，仍需作为密钥保密 |
| `ANDROID_KEYSTORE_PASSWORD` | keystore 密码 |
| `ANDROID_KEY_ALIAS` | release 密钥别名 |
| `ANDROID_KEY_PASSWORD` | 该密钥密码 |

例如在 macOS 本地可用 `base64 -i android/keystore/tamayura-personal-release.jks | pbcopy` 复制编码后粘贴到对应 Secret；不要将编码、密码或私钥写进 Git、发布说明或聊天记录。另三项分别从拥有者的当前签名配置填入，无需将整个 `key.properties` 上传。切换本地签名配置不会自动更新远端 Secrets；若此前配置过旧密钥，应同步替换上述四项后再发布。

工作流使用 GitHub 自动提供的 `GITHUB_TOKEN`，不需要个人访问令牌。默认仅有 `contents: read`，最终发布 job 才授予 `contents: write`；仓库或组织策略需允许 Actions 运行及发布 Release。上述签名 Secrets 和权限属于首次配置；完成后每次发布沿用现有配置，只有密钥或策略发生实际变化时才维护，不重复要求用户设置、登录或批准。

`configure-android-signing.py` 在 Android runner 临时生成 `android/key.properties` 与 `android/keystore/ci-release.jks`，不打印 Secret；缺失配置、无效 Base64 或已有本地签名文件均停止，不回退为 debug 签名。构建结束后用 `always()` 清理临时文件，上传附件只包含已核验的 APK 和校验和。

### 每次发布的固定顺序

发布按以下四步执行，不把“推送代码”“本地打包”“推送 Tag”或“Actions 已启动”单独视为发布完成。仅讨论或维护发布流程时不执行发布；已获得某版本的发布授权后，由 Agent 连续执行并等待结果，无需用户逐步确认或人工下载产物。使用现有 Git 推送权限、签名 Secrets 与工作流 `GITHUB_TOKEN`；不以 Chrome 下载、安装 `gh`、申请个人 API 令牌或新 OAuth 授权作为每次发布前提。预检发现实际遗漏、版本冲突或缺少必要条件时，先说明问题，不跳过检查或提前推送 Tag。

1. **修改 CHANGELOG、版本及相关文档，commit 并 push 到 GitHub 的 `main`。** 先检查工作区、同步远端 `main`，保留并核对未提交改动，不覆盖其他任务的工作。确认目标 Tag / Release 尚不存在、现有推送权限与 Actions 可用，沿用已配置的四项 Android Secrets。更新 `pubspec.yaml` 的版本和构建号，例如 `0.6.0+9`；这只是示例，不由工作流自动递增。将未发布内容归入唯一的 `## 0.6.0`，填写真实日期、功能、改进、修复及已知限制，顶部保留空的 `## unstaged`；同步发布记录及必要的双语 README。版本正文需说明当前签名、安装/数据影响和未完成的真机验收，不提前声称测试或发布成功。将本次源码、工作流、版本和文档一起提交，遵守 `AGENTS.md` 的共同作者署名要求，推送 `main` 后记录完整提交 SHA，作为后续打包和 Tag 的唯一目标。

   发布工作流必须随目标提交进入默认分支 `main`，不能只留在未合并的发布分支。仅推送 `main` 不会创建 Release；它会触发日常分支 CI。

2. **对该已推送提交执行本地完整测试、打包和核验。** 从该提交准备干净的构建目录，使用约定 SDK 和锁定依赖，不混入未提交源码或历史产物。执行下文发布工具回归、actionlint 工作流检查及平台完整打包流程，覆盖格式、静态分析、当前全部 Flutter 测试、适用原生测试、Release 构建及产物核验；不得以旧版本通过记录、只跑新增测试或只编译成功替代。核验版本与构建号、最低系统、架构、签名、归档内容、环境隐私和 SHA-256，记录实际执行范围。

   本地 macOS 主机执行 `scripts/package-android.sh` 和 `scripts/package-macos.sh`；Windows 必须在 x64 Windows 环境执行 `scripts/package-windows.ps1` 并完成源码白名单检查。本机无法执行 Windows 原生流程时，以第 1 步同一提交的 **Windows preview** 分支 CI 完整测试、打包及自动核验成功为门槛，无需将其 artifact 下载到本地重复验证；结果注明由 Windows CI 完成，不能称为本机 Windows 构建，也不能用源码 ZIP 替代。已触发的三平台分支 CI 均须成功，不忽略失败或仍在运行的检查。

   任一测试、构建或核验失败，先修复并回到第 1 步提交、推送，再针对新提交重新执行第 2 步。若准备打 Tag 的提交发生变化，包括版本、工作流或文档变化，也须重新完成本步骤；不得给未经本轮验证的新提交打 Tag。本地打包阶段不调用发布脚本创建远端 Release，最终上传的包由 Tag 工作流重新构建。

3. **在 `main` 上为已验证提交创建版本 Tag，并推送到 GitHub。** 重新确认工作区没有待发布的未提交变更，本地 `main`、远端 `main` 与第 2 步记录的提交 SHA 一致，版本与 CHANGELOG 匹配，目标 Tag / Release 不存在。若远端 `main` 已前进，先同步并回到前两步，不把 Tag 随手打到新的 HEAD。使用附注 Tag，显式指定经过核验的提交，再单独推送该 Tag；不得强制推送或移动版本 Tag。以下命令仅为 `0.6.0` 示例，只有前两步全部通过后才能执行：

   ```sh
   # release_commit 为第 2 步已验证且与本地、远端 main 一致的完整提交 SHA。
   git tag -a v0.6.0 "$release_commit" -m "Tamayura v0.6.0"
   git push origin v0.6.0
   ```

   创建本地 Tag 不会启动自动发布；成功推送 Tag 才会触发 **Publish release**。

4. **等待 GitHub 自动发布完成，并由 Agent 核对发布状态与元信息。** 等待该 Tag 的 **Publish release** 中准备、Android、macOS、Windows 和发布五个 job 全部成功，再按下方清单核对 Tag、提交、正文与五个附件的元信息。测试、构建、签名、完整性、SHA-256 和上传结果由 CI 自动核验，不再把产物下载到本地重复手工比对。只有工作流全部成功且远端内容一致才能报告完成。当前工作流发布 **Pre-release**，不标记 Latest；这是现有试用分发策略，稳定公开发行需先接入相应签名、公证和验收。

### 远端发布完成的核验清单

| 核验项 | 完成条件 |
| --- | --- |
| Actions 结果 | 对应 Tag 的准备、Android、macOS、Windows、发布五个 job 均成功；发布 job 已完成自动校验和上传，不以部分 job 成功代替 |
| Tag 与源码 | 将远端附注 Tag 解析到实际提交后，其 SHA 与第 2 步验证提交、对应 Actions 运行的提交一致；不以可能已继续前进的 `main` HEAD 或 Release 的分支名字段代替提交核对 |
| Release 状态与正文 | 版本 Tag 正确、非草稿，当前策略为 Pre-release；正文与 **Tag 内** `CHANGELOG.md` 对应版本段落的提取结果一致，不含其他版本或 `unstaged`，不用发布后工作区的 CHANGELOG 代替 |
| 三个平台包 | 恰有 `Tamayura-<version>-android.apk`、`Tamayura-<version>-macos.zip`、`Tamayura-<version>-windows-x64.zip`，均为成功上传的非空文件 |
| 两个校验/元数据附件 | 恰有 `SHA256SUMS` 和 `release.json`；加上三个包，共五个工作流上传附件。GitHub 自动提供的 Source code ZIP / tar.gz 不计入这五个附件 |
| CI 中的完整性与元数据 | 三平台打包脚本完成版本、系统、架构、签名和归档检查并生成独立 SHA-256；发布 job 校验同一运行的三个包后生成联合 `SHA256SUMS` 和 `release.json` |
| 上传结果 | 发布脚本通过 GitHub API 核对五个附件的名称、大小、上传状态，以及 API 提供时的 SHA-256 digest；Agent 读取 Release 附件元信息确认集合一致，不另行下载附件 |

`release-metadata.py assemble` 在 CI 内逐项验证三个包的独立校验和与文件名，并生成统一版本、构建号、平台信息、字节数及 SHA-256。`SHA256SUMS` 覆盖三个包；`release.json` 由这些已验证文件生成。Android 构建使用此前按当前本地密钥配置的四项 Secrets，自动验签并拒绝 debug 签名；CI 不读取本地 keystore，也不执行跨主机证书指纹比对，不再要求 Agent 下载 APK 重新验签。发布脚本在上传后自动核对五个附件的状态、大小和可用摘要，全部符合才公开 Release。

本地构建和 CI 构建不要求二进制逐字节相同。Agent 依据实际 CI 结果与远端元信息完成验收；没有下载就不得表述为“下载校验通过”。任一 CI 检查失败、附件缺失或正文/提交不符时，停在对应失败步骤处理，可在现有授权内安全重试；不能跳过校验、静默替换已公开附件或移动 Tag。

全部核验通过后，报告 Release 链接、Tag 对应提交、Actions 结果及五个附件的自动核验结果，明确未另行下载复验和实际真机验收范围。发布前文档中尚未完成的动作保留真实状态；发布后的实际结果补充到 `docs/releases/<版本号>.md`，作为后续记录提交，不修改既有 Tag 或将后来结果伪装成打 Tag 前已完成。

当 `unstaged` 存在未发布功能时，即使 `pubspec.yaml` 暂时保持已有版本号，也不能直接用该旧版本 Tag 发布当前源码。校验会拒绝未归档内容、版本不一致、缺失/重复/空的版本说明，以及非最新版本段落。空的分类标题可留在 `unstaged`；版本说明按二级标题边界提取，代码块中的标题不会截断正文。

### 测试、产物与失败处理

Android SDK 初始化须为 `setup-android@v3` 显式指定 `packages: platform-tools`，再安装 `platforms;android-36` 和 `build-tools;36.0.0`。日常 Android 分支 CI 与 Tag 发布采用相同的初始化和 API 36 安装步骤，在推送 Tag 前验证环境配置。该 Action 的旧默认值包含 Google 已移除的 `tools` 包，会在测试前失败；不要依赖盲目重跑恢复。原因见[上游修复说明](https://github.com/android-actions/setup-android/pull/538)。

流程先运行发布工具的回归测试，再用 `release-metadata.py prepare` 校验 Tag、应用版本和 CHANGELOG。三个独立 job 随后并行执行：

| 平台 | 检查与构建 | 上传至 Release 的文件 |
| --- | --- | --- |
| Android | 公共检查、Flutter 全量测试、API 36 原生测试、专用签名 Release 构建；核验应用 ID、版本、最低/目标系统、ABI、签名及 16 KiB 对齐 | `Tamayura-<version>-android.apk` |
| macOS | 公共检查、Flutter 全量测试、macOS 原生检查、Universal Release 构建与 ad-hoc 签名核验 | `Tamayura-<version>-macos.zip` |
| Windows | 公共检查、Flutter 全量测试、源码白名单检查、原生 CTest、x64 Release 构建与完整归档核验 | `Tamayura-<version>-windows-x64.zip` |

每个平台先保存运行内的 Actions artifact，保留 7 天。发布 job 只下载同一次运行的三个指定产物，核对独立校验和、文件名和完整性，再用 `release-metadata.py assemble` 生成联合 `SHA256SUMS` 和 `release.json`。Release 共包含三个包及这两个元数据文件，不包含源码交接 ZIP、测试日志、签名配置或私钥。`release.json` 记录版本、构建号、各包大小、SHA-256、平台要求、签名和自动化验证范围；不会把自动化完成标记成真机验收完成。

Release 正文直接使用对应 `CHANGELOG.md` 版本段落，不使用提交列表自动生成说明，也不拼接 `unstaged` 或其他版本。发布脚本先建立草稿，通过 GitHub API 核对全部五个附件的名称、大小、上传状态及可用 SHA-256 digest 后再公开，避免用户看到缺少平台包的版本。任一平台测试、构建或校验失败均不进入发布；上传失败保留草稿，Agent 可自动重跑同一提交的失败 job。重跑只允许继续对应源码提交的草稿，已公开版本不会被自动覆盖；Tag 若被移动到另一提交会拒绝发布。需要修改源码或工作流时应准备新版本和新 Tag，重新执行完整流程，不移动既有版本 Tag。

发布工具的本地回归入口为：

```sh
for test_file in scripts/test-*.py; do
  python3 "$test_file" || exit 1
done
```

日常 Android CI 同时执行这些回归及 actionlint 工作流检查。脚本回归采用隔离测试数据和模拟外部服务，不会读取本地私钥或实际创建 Release；它们不代替三平台真实构建、签名核验和跨设备验收。发布脚本直接调用 GitHub REST API，无需安装 `gh`；维护时参考 [Release API 与目标提交权限](https://docs.github.com/en/rest/releases/releases#create-a-release) 和 [工作流权限](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)。

本地工作流检查使用 actionlint 1.7.12，安装该版本后在根目录执行 `actionlint`；也可使用与 Android CI 相同的 `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:1.7.12 -color`。检查对象包括本次发布工作流，不能只运行应用测试而跳过发布工具与工作流检查。

## 统一工具链与检查

使用正式 **Flutter 3.47.6 stable / Dart 3.13.5**，依赖由 `pubspec.lock` 固定。先检查 `flutter --version`，依赖解析与后续构建使用同一 SDK。macOS 使用 Swift Package Manager，不混用另一份 Flutter checkout 生成的 `package_config.json`。

```sh
FLUTTER_SWIFT_PACKAGE_MANAGER=true flutter pub get --enforce-lockfile
dart format --output=none --set-exit-if-changed lib test
flutter analyze --no-pub
flutter test --no-pub --coverage
```

离线且依赖缓存齐全时可用 `flutter pub get --offline --enforce-lockfile`。本轮同一提交、同一工具链和锁定依赖下的公共检查可以避免手工重复执行，但不能修改打包脚本来跳过它们自带的检查；各平台的原生测试、Release 构建和产物核验仍须执行。独立调用打包脚本时，脚本会自行执行完整检查。

## Android

最低 Android 16（API 36），不支持 Android 15 及更早版本。需要 Android SDK / Build Tools 36、JDK 21；源码编译目标为 Java 17。Robolectric API 36 测试需 Java 21 或更新版本。如 Gradle 与测试使用不同版本 JDK，可通过临时 Gradle init 脚本指定测试 JVM；发布记录仅保留版本和测试结果，不记录个人安装路径。

```sh
scripts/package-android.sh
```

脚本执行公共检查、Flutter 全量测试及覆盖率、`testDebugUnitTest` 原生测试和 Release 构建，输出 `dist/<version>/Tamayura-<version>-android.apk` 与 `SHA256SUMS-android`，并调用 `aapt`、`apksigner` 和 `zipalign` 核验。确认应用 ID `dev.tamayura.app`、versionName / versionCode 与 `pubspec.yaml` 一致、minSdk / targetSdk `36`，通用 APK 包含 arm64-v8a / armeabi-v7a / x86_64。确认不可调试、release 验签与 16 KiB 对齐通过，拒绝 debug 签名。首次配置及密钥变更时确保本地签名与四项 Secrets 使用同一密钥；日常发布自动沿用该配置，不要求再次人工比对本地证书与远端 APK，也不得声称 CI 自动执行了跨主机指纹比对。

0.6.0 起的 release 构建改用个人签名证书：主体仅包含 `CN=poppinzhang`，其余主体字段省略；密钥库为 `android/keystore/tamayura-personal-release.jks`（PKCS12，别名 `tamayura-personal-release`，RSA 3072、SHA256withRSA，有效期 10,000 天）。由 `android/key.properties` 配置，`storeFile` 相对 `android/app` 解析，值为 `../keystore/tamayura-personal-release.jks`。姓名属于公开证书内容，会随安装包分发。

旧密钥库 `android/keystore/tamayura-release.jks` 保留，原签名配置备份为 `android/keystore/previous-release-key.properties`。0.5.0 及更早的既有安装包保持旧签名，不重新签署或替换历史产物。新旧证书之间未设置签名轮换机制，换用新密钥的安装包不能覆盖旧签名安装；首次切换需卸载旧版再安装，后续使用同一新密钥签名的版本才可覆盖安装。

密钥库与配置文件权限为 `0600`，密钥目录为 `0700`。强随机密码仅保存于本地受限权限配置，不能打印到终端或日志；私钥、密码及配置备份不得提交 Git 或复制到分发目录。应单独安全备份密钥及其密码，以便后续继续使用同一签名。缺少 release 签名配置时不得回退到 debug 签名。公开证书指纹可记录在验证文件中，私钥和密码不可分发。

当前个人证书有效期为 **2026-10-17 至 2054-03-04**，公开证书 SHA-256 指纹为 `9DC47DF9E7DB5106453C2A1D032B69B5BC6110122C7B6E4F5A0912504D8C7B2F`。Agent 可在本地打包时自动核对公开指纹；CI 使用已配置的 Secrets，执行 APK 验签并拒绝 debug 签名，不以历史验签记录替代本次检查。首次配置或换钥时才确认 Secrets 与本地密钥来源一致，不作为每次发布的人工门槛，也不要求发布后下载 APK 再次验签；记录中区分实际执行的本地指纹核对和 CI 验签。

如需按 ABI 拆分或商店包，可另外执行 `flutter build apk --release --split-per-abi` 或 `flutter build appbundle --release`；本次本地交付为通用 APK，生成 AAB 不代表已经上架。

## macOS

最低 **Sequoia 15.0**，支持 Tahoe 26 及后续版本。需要完整 Xcode 和 macOS SDK；仅 Command Line Tools 无法完成构建。插件使用 Swift Package Manager。

```sh
scripts/package-macos.sh
```

脚本执行公共检查、`scripts/test-macos-native.sh`、`flutter build macos --release --no-pub`，随后核验版本、最低系统、Universal 架构和签名，生成 `dist/<version>/Tamayura-<version>-macos.zip` 与 `SHA256SUMS-macos`。它不会覆盖其他平台的联合校验文件。

脚本兼容 macOS 自带的 Bash 3.2。中文提示中紧邻标点的变量使用 `${name}` 明确边界，避免 UTF-8 环境将标点字节误读为变量名，导致打包成功后仍以 `unbound variable` 失败，或掩盖版本校验的原始报错。

默认使用 `lib/main.dart` 正常入口与 `dev.tamayura.app` Bundle ID。原生 RunnerTests 如使用独立 Bundle、空 Dart 入口和隔离 DerivedData，只能记为原生宿主测试；正式 Release 必须重新使用正常入口构建，不能将测试宿主归档为应用。

本地 ad-hoc 打包还需去除主程序的原生调试符号（`strip -S`），避免插件缓存路径进入发行包，再按项目 `Release.entitlements` 重新 ad-hoc 签名；该流程须拒绝非 ad-hoc 输入，避免覆盖 Developer ID 等既有签名。公开签名发行应使用对应的独立签名与公证流程。

核验主程序、App.framework 与 FlutterMacOS.framework 含 arm64 / x86_64；检查 CFBundle 版本、最低系统 15.0、`codesign --verify --deep --strict`、ZIP CRC，并在解压副本上再次核验签名、版本和架构。`xcode-select` 指向 Command Line Tools 时，脚本自动为当前进程选用标准 `/Applications/Xcode.app/Contents/Developer`，不修改全局设置；非标准位置可传 `DEVELOPER_DIR`。

当前为 ad-hoc 本地签名、未公证。正式公开分发还需拥有者的 Developer ID、Hardened Runtime、签名与公证；ZIP 本身不是公证版本或 App Store 发布。详情见 [macOS 实现与验收](macOS原型.md)。

## Windows

目标为 Windows 10 1809+ / Windows 11 x64。必须使用 Windows 构建环境，并安装 Flutter 3.47.6、Visual Studio 2022 的“使用 C++ 的桌面开发”、Windows SDK 与 CMake。

也可使用 Visual Studio 2022 Build Tools：安装 `Microsoft.VisualStudio.Workload.VCTools`、`Microsoft.VisualStudio.Component.VC.Tools.x86.x64`、`Microsoft.VisualStudio.Component.VC.CMake.Project` 和 `Microsoft.VisualStudio.Component.Windows11SDK.26100`。可使用 Build Tools 17.14、MSVC 19.44 和 Windows SDK 10.0.26100.0；不需要 Android SDK 或 JDK。Flutter SDK、Git 和项目可以放在独立任务目录，仅为当前构建进程设置 PATH。工具链安装后先运行 `flutter precache --windows`，首次解析使用 `flutter pub get --enforce-lockfile` 并核对构建后的锁文件。

```powershell
flutter doctor -v
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\package-windows.ps1
```

脚本要求 x64 Windows 构建主机，执行格式、分析、Flutter 全量测试、Windows 原生 CTest 和 x64 Release 构建，按 `pubspec.yaml` 核对 EXE 数字版本 `<主版本>.<次版本>.<修订号>.<构建号>`，将完整 `build/windows/x64/runner/Release` 归档为 `dist/<version>/Tamayura-<version>-windows-x64.zip`，并生成 `SHA256SUMS-windows`。Flutter 3.47.6 通过主机架构选择 Windows 目标，不接受 `build windows --target-platform`。任何检查失败都会终止。SQLite 原生资产、插件 DLL、Flutter 引擎和 `data` 必须随包保留，不能只发送 EXE。

`.github/workflows/windows.yml` 使用 `windows-2022` 执行同一流程并上传构建产物。使用前需有可访问的远端仓库；配置文件存在不代表 CI 已运行或产物已生成。

Windows 发行目录不包含 Flutter 测试专用的根 `native_assets.json`（其中含构建机绝对路径）；正式运行清单 `data/flutter_assets/NativeAssetsManifest.json` 和包根 `sqlite3.dll` 必须保留。CMake 同时排除新复制与清理旧构建残留，打包脚本显式核验这两个条件。解压后的启动检查需确认进程实际加载解压目录的 SQLite，避免构建机缓存掩盖缺失依赖。

Mac 可执行下列命令制作构建输入：

```sh
python3 scripts/test-windows-source.py
python3 scripts/package-windows-source.py
```

产物 `Tamayura-<version>-windows-source.zip` 和 `SHA256SUMS-windows-source` 使用源码白名单，排除其他平台原生工程、密钥、本机 SDK 配置、构建缓存和用户媒体。它不能作为 Windows 可执行发行包。Windows ZIP 当前为未签名试用包，无安装器、MSIX 或 Store 发布，需要相应 Visual C++ x64 运行库；首次联网只对可信专用网络授权防火墙。详情见 [Windows 实现与调试](Windows原型.md)。

## 统一校验与发布元数据

各平台脚本对实际生成的包计算独立 SHA-256；Tag 发布 job 只接收同一次运行的三个平台产物，调用 `release-metadata.py assemble` 验证完整集合和各包校验和，再自动生成 `SHA256SUMS` 与 `release.json`。缺少任一平台或哈希不符时停止，不发布残缺的远端 Release。本地流程仅留存实际完成的平台包及独立校验和，不需要下载 Windows CI 产物凑齐本地集合，也不增加人工汇总步骤。

`release.json` 记录统一版本、构建号、日期、每个平台状态、最低系统、架构、产物文件名、字节数、SHA-256、签名和实际验证结果；元数据、版本说明与 CI 目录文件保持一致。发布脚本随后自动核验 GitHub 上传结果。源码辅助包使用独立校验文件，不能混作已交付的可执行平台。

## 安装、数据与验收

0.7.0 沿用 0.6.1 的协议 v4、媒体库 schema 7 和独立下载任务库 schema 3，本次不更改 schema 或协议，也不主动清空现有数据库。自动同步改用分钟配置，不读取或转换旧小时配置；尚未保存分钟配置时使用默认 10 分钟。

协议 v4 与 0.5.0 的协议 v3 不互通。0.6.1 已将媒体库升至 schema 7，从更早 schema 安装升级时仍会直接清空重建媒体库：清空设置、记住的设备、离线相册与缩略图、下载历史索引，需要重新选择目录并发现设备，新发现的设备需要确认同步。媒体库重建不清空独立下载任务库；卸载或清空应用数据则会清除任务与未完成分片。v1.0.0 前不承诺不同应用版本或旧数据兼容，不增加历史迁移、旧协议适配或回退逻辑。允许同签名覆盖安装；遇到不兼容可以清空应用数据或卸载重装。外部原始媒体和已保存的接收文件保留。

Android release 仅在新旧安装包签名相同时可使用 `adb install -r <本次安装包路径>` 覆盖安装。0.7.0 沿用 0.6.1 的专用 release 证书及现有 CI Secrets，不切换密钥。该证书与既有 0.5.0 及更早安装包签名不同，首次切换必须先卸载旧版再安装；debug 与 release 的签名冲突同样需要先卸载。卸载会清除设置、SAF 目录授权、缓存、下载记录及未完成分片，需重新选择目录并发现设备；用户选择的外部共享目录和已保存接收文件保留。签名变更后 `ANDROID_ID` 可能改变，其他设备可能将其识别为新设备。此处不提供旧签名兼容或轮换流程。

macOS 完整解压 ZIP，将 App 放入“应用程序”；本地未公证包若被系统拦截，在确认来源和校验后通过系统“隐私与安全性”确认，不关闭全局 Gatekeeper。Windows 完整解压 ZIP 后运行 EXE。

互联设备使用相同版本。在真实 Android 16+、macOS 15.0+、Windows 目标系统完成自动发现、目录权限、离线缓存、小照片与大视频、取消续传、断网/睡眠恢复、后台共享和文件完整性验收。扫码与系统分享仅按各平台支持范围验收。Sequoia/Intel、厂商 Android 电源策略和 Windows 防火墙/运行库仍需真实环境验证，自动化不能替代。

发布清单：公共与适用平台测试通过；Release 包版本、签名、架构、最低系统、校验和正确；试用性质及未完成验收清晰；分发目录不含密钥、密码、绝对 SDK 配置或用户照片。正式公开发布前还需干净环境或 CI 重建。
