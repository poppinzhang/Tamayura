# 发布与打包

## Windows 构建（未发布）

当前 Windows 实现基于 `0.3.0+6`，未提升版本或创建发布；变更保留在 `CHANGELOG.md` 的 `unstaged`。目标为 Windows 10 1809+ / Windows 11 x64，使用 Flutter 3.47.6、Visual Studio 2022 的「使用 C++ 的桌面开发」、Windows SDK 与 CMake。必须在 Windows 构建和调试，不能把 macOS 上的源码检查当作 Windows 验收。

```powershell
flutter doctor -v
flutter pub get
flutter run -d windows
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\package-windows.ps1
```

打包脚本依次运行格式检查、静态分析、Flutter 全量测试、Windows 原生 CTest，再构建 Windows x64 Release；任何步骤失败都会停止。核对 EXE 的版本后，将完整 `build/windows/x64/runner/Release` 归档为 `dist/<版本号>/Tamayura-<版本号>-windows-x64.zip`，并生成 `SHA256SUMS-windows`；不覆盖既有 Android/macOS 联合校验文件。SQLite 使用 Flutter 原生资产随 Release 目录交付，插件 DLL、引擎及 `data` 也必须保留，不可只发送 EXE。

Windows 预览包为未签名 ZIP，无安装器或 Store 发布；接收者须完整解压，并具备 Microsoft Visual C++ x64 运行库。首次连接仅允许应用通过专用网络防火墙。当前 Windows 原生编译、测试、运行和实际局域网互传尚待验证；`.github/workflows/windows.yml` 使用 `windows-2022` 执行同一脚本，配置存在不代表远端执行通过。

从 Mac 交付源码可执行 `python3 scripts/test-windows-source.py` 与 `python3 scripts/package-windows-source.py`，生成 `dist/<版本号>/Tamayura-<版本号>-windows-source.zip` 和 `SHA256SUMS-windows-source`。源码白名单包括 Windows 工程、Dart 代码、资源、测试、锁文件与说明，不带 Android/macOS 工程、密钥、本地 SDK 配置或构建缓存。该包不能作为 Windows 可执行发行包。

Windows 发行前须通过上述自动化检查，并完成 Windows ↔ Android/macOS 的发现、目录边界、离线缓存、照片/大视频下载、文件完整性、取消续传、睡眠唤醒、后台共享与防火墙验收；安装后的干净机器还需验证运行库及完整 ZIP。实现、运行库链接和逐项调试清单见 [Windows 实现与本机调试](Windows原型.md)。

## macOS 构建

macOS 最低 **Sequoia 15.0**，支持 Tahoe 26 及后续版本。0.3.0 首次与 Android 一起交付 macOS 本地签名试用包；实现与验收见 [macOS 实现](macOS原型.md)。

需要完整 Xcode 与 macOS SDK、Flutter 3.47.6；Command Line Tools 无法完成 App 构建。插件使用 Swift Package Manager，本地运行与打包应启用同一插件解析方式：

```sh
FLUTTER_SWIFT_PACKAGE_MANAGER=true flutter pub get
FLUTTER_SWIFT_PACKAGE_MANAGER=true flutter run -d macos
scripts/package-macos.sh
```

打包脚本要求格式、分析、Flutter 全量测试与 macOS 原生测试通过，再构建 `build/macos/Build/Products/Release/Tamayura.app`，核对最低系统 15.0、版本、arm64 / x86_64 架构与代码签名。按 `pubspec.yaml` 版本生成 `dist/<版本号>/Tamayura-<版本号>-macos.zip` 及 `SHA256SUMS-macos` 独立校验文件，避免覆盖同目录的双端 `SHA256SUMS`；本次 ZIP 路径为 `dist/0.3.0/Tamayura-0.3.0-macos.zip`。CI 工作流为 `.github/workflows/macos.yml`，配置存在不表示已执行通过。

脚本在 `xcode-select` 仍选择 Command Line Tools 时，为当前进程自动设置 `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`，不修改系统选择；非标准安装位置可自行传入 `DEVELOPER_DIR`。

macOS 本地试用包使用 ad-hoc 签名，未进行公证。正式公开分发前需配置拥有者的 Developer ID、Hardened Runtime、签名与公证，并完成 Sequoia/Tahoe 和 Mac ↔ Android 双向验收。本地 ZIP 不属于公证版本或 App Store 发布；本地开发不需要预先加入账号或证书密钥。

## 本地 release 签名

0.3.0 沿用 0.0.1、0.0.2、0.1.0、0.2.0 的专用本地 release keystore，不使用 Android debug 证书：

- 密钥文件：`android/keystore/tamayura-release.jks`，实际存储格式为 PKCS12。
- 别名：`tamayura-release`；算法 RSA，密钥长度 3072 位，有效期 10000 天。
- 签名配置：`android/key.properties`。
- 密钥与配置文件权限为 `0600`，密钥目录为 `0700`。
- 以上文件均由 `.gitignore` 排除，不能复制到 `dist/`、提交到版本库或附在发布包中。

`android/key.properties` 的字段如下；示例中的密码只是占位，实际密码不写进文档：

```properties
storeFile=../keystore/tamayura-release.jks
storePassword=YOUR_STORE_PASSWORD
keyAlias=tamayura-release
keyPassword=YOUR_KEY_PASSWORD
```

`storeFile` 按 `android/app` 为基准解析，因此上述相对路径指向 `android/keystore/tamayura-release.jks`。安全备份密钥及其密码，后续发布继续使用该签名证书。

## 试用 APK 打包

确认 `pubspec.yaml` 为 `0.3.0+6`、全部自动化测试通过并配置签名后，构建通用 APK：

```sh
flutter build apk --release
mkdir -p dist/0.3.0
cp build/app/outputs/flutter-apk/app-release.apk dist/0.3.0/Tamayura-0.3.0-android.apk
```

验签和检查包信息时，使用 Android SDK Build Tools 中的 `apksigner`、`aapt`：

```sh
apksigner verify --verbose --print-certs dist/0.3.0/Tamayura-0.3.0-android.apk
aapt dump badging dist/0.3.0/Tamayura-0.3.0-android.apk
```

确认应用 ID `dev.tamayura.app`、versionName `0.3.0`、versionCode `6`、最低 API `36`，并核对实际签名为专用 release 证书。版本说明中记录产物大小与验证结果。macOS ZIP 也生成并校验后，在产物目录统一生成双端校验文件：

```sh
(cd dist/0.3.0 && shasum -a 256 Tamayura-0.3.0-android.apk Tamayura-0.3.0-macos.zip > SHA256SUMS)
(cd dist/0.3.0 && shasum -a 256 -c SHA256SUMS)
```

将版本号、日期、应用 ID、最低系统、ABI、产物文件名、字节数、SHA-256 及实际验证结果写入 `release.json`，与 APK、macOS ZIP、校验文件和版本说明逐项核对。

Linux 可使用 `sha256sum` 生成并校验相同格式的文件。没有 `key.properties` 时，release 构建不得回退到 debug 签名冒充试用发布包。

如以后需要按 ABI 分包或 AAB，可单独构建；本次交付使用通用 APK：

```sh
flutter build apk --release --split-per-abi
flutter build appbundle --release
```

这些产物分别位于 `build/app/outputs/flutter-apk/` 和 `build/app/outputs/bundle/release/`。构建 AAB 不代表已经上传商店。

## 安装与测试

首次安装：

```sh
adb install dist/0.3.0/Tamayura-0.3.0-android.apk
```

已安装同签名的版本且版本号满足 Android 安装要求时，可以覆盖安装。覆盖安装通常保留应用数据，但不代表当前代码必须兼容这些旧数据：

```sh
adb install -r dist/0.3.0/Tamayura-0.3.0-android.apk
```

0.3.0 使用协议 v3，媒体库 schema 升至 4，下载任务库仍为 schema 2。媒体库按 v1.0.0 前策略清空重建，不迁移旧缓存和设置；覆盖安装后仍需重新选择共享与接收目录、发现设备。外部共享照片和已保存的接收文件保留。双方设备应安装相同版本，不保证不同应用版本间的行为兼容。

Android 沿用系统 `ANDROID_ID` 设备身份，macOS 使用本地保存的独立 UUID。清除媒体库不为旧随机 UUID 设备记录提供迁移；目录授权或历史记录不兼容时需按当前版本重新配置。

macOS 解压 `dist/0.3.0/Tamayura-0.3.0-macos.zip`，将 `Tamayura.app` 放入「应用程序」后打开。该包为本地 ad-hoc 签名、未公证；如系统阻止首次打开，只在确认来源和校验结果后通过系统「隐私与安全性」页面确认，无需关闭全局 Gatekeeper。

若旧配置等仍与当前逻辑不兼容，可以清空应用数据或卸载重装。调试版与 release 版签名不同时需卸载后再安装：

```sh
adb uninstall dev.tamayura.app
adb install dist/0.3.0/Tamayura-0.3.0-android.apk
```

卸载会清除应用设置、SAF 目录授权、缓存缩略图、下载记录和未完成分片。原始共享照片及已保存到外部接收目录的文件会保留；重新安装后需重新选择目录和发现设备。

测试验证当前版本的功能与异常处理，不要求验证历史版本兼容或数据迁移路径。清空或重建数据库属于可接受的处理方式，不要求为保留旧版本数据实现迁移逻辑。

- 分发目录和版本库不包含 keystore、密码、绝对 SDK 路径或用户照片。
