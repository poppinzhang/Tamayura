# Tailscale 接入需求

状态：2026-11-15 开始实现。本文保留需求、原设计建议与验收目标，不表示所有验收项均已完成。当前代码、实际接口、安全边界和已执行检查统一见 [Tailscale 实现](Tailscale实现.md)；1.1.0 安装包不包含本次接入。

## 已确定的需求与范围

| 需求 | 目标行为 |
| --- | --- |
| 设置中登录 | 「设置」增加 Tailscale 登录入口；登录是可选能力，不登录、登录失败或退出登录均不影响原有局域网能力 |
| 发现远端设备 | 「设备」能够发现当前 Tailscale 网络中可见、允许访问且正在运行 Tamayura 服务的其他设备；可行性与实现边界见下文 |
| 明确在线路径 | 分别显示「局域网在线」和「Tailscale 在线」；同一设备两条路径均可用时同时显示，不重复创建设备 |
| 功能体验一致 | 通过 Tailscale 完成相册元数据与缩略图同步、浏览、原文件下载到本地及恢复重试，沿用局域网的操作入口和业务规则 |
| 发现与连接优先级 | 先检查局域网能否发现并连接已记住设备；本机互联网可用后检查 Tailscale 注册与就绪状态，就绪后查询远端候选，也可发现此前未记住的 Tamayura 设备；同一设备新操作优先使用可达的 LAN 路径 |

沿用前述讨论的 `tsnet` 内嵌方向：由 Tamayura 管理自己的 Tailscale 节点，目标是用户只安装 Tamayura 即可使用，不要求另装系统 Tailscale 客户端。Flutter 与 Go 的具体桥接方式仍须验证；可以先用官方客户端验证目标线路，但这不算完成应用内接入。

第一阶段只连接官方管控服务，不提供自定义控制服务器地址、Headscale 配置或多账号同时在线。未来有需求时再开放自建 Headscale；内部设计应区分管控服务、网络身份和连接状态，避免将官方地址散落在业务层，也不能把这种预留写成已经支持 Headscale。

目标覆盖当前已有的 Android、macOS、Windows、Linux 平台；优先验证 Android 手机与 Windows 家庭 NAS，其他平台分别验证后再声明支持。iOS 仍是后续平台目标。Windows NAS 沿用当前桌面应用，不新增专用 NAS 服务端、系统服务或远程唤醒。

## 设置页面与登录生命周期

设置页新增 Tailscale 区域，展示登录状态、当前网络连接情况以及必要的操作。以下文案为中文语义草案，实现时统一提供简体中文、日本語和 English，并遵循 [多语言](多语言.md)。

| 状态 | 展示与操作 | 对局域网的影响 |
| --- | --- | --- |
| 未登录 | 「未登录」与「登录 Tailscale」；说明登录后可连接远端设备 | 无；正常发现、共享、同步和下载 |
| 正在登录 | 展示进度，打开系统浏览器完成官方认证；提供重新打开认证页面、取消操作 | 不阻塞局域网启动或正在进行的任务 |
| 等待设备批准 | 如 tailnet 开启设备审批，明确说明等待批准，不能提前显示已连接 | 局域网继续可用 |
| 已登录且连接正常 | 显示账号 / 网络名称及「已连接」，提供退出登录 | 局域网与 Tailscale 并行工作 |
| 已登录但连接异常 | 保留账号信息，说明网络不可达、管控连接异常等实际已知原因，提供重试 | 仅影响相关 Tailscale 能力 |
| 需要重新认证 | 凭据到期、节点撤销等可确定原因分别提示，提供重新登录 | 不要求先登录才能使用局域网 |

登录身份与网络健康应分别记录。管控暂时不可达不等于用户已经退出登录，也不能据此把仍可通信的全部 Tailscale 对端立即标为离线；后续服务可用性以实际路径检查为准。

首次登录通过官方认证页面完成，Tamayura 不收集 Google 等身份提供方的密码，不内置全体用户共用的认证密钥或管理令牌。应用重启后恢复本机节点身份，不重复注册新节点；需要重新认证时再提示用户。授权链接、私钥和令牌不写入普通日志、二维码或媒体数据库，不随打包产物分发。[tsnet 认证与状态](https://tailscale.com/docs/features/tsnet)

未登录时不启动 Tailscale 组网与远端扫描，也不因该模块初始化失败中止 Tamayura 主界面或局域网服务。已有登录状态的启动与重连在独立生命周期内完成，不等待它成功才启动局域网。

退出登录与切换账号遵循以下数据边界：

- 停止当前内嵌节点的远端发现、监听和连接，清除可再次自动登录旧身份的本机凭据；不停止局域网服务。临时网络故障不执行该清理。
- 保留 Tamayura 设备记录、已同步相册、缩略图、已下载文件及未完成分片。退出 Tailscale 不等于「忘记设备」，也不等于删除本地媒体。
- 仅有 Tailscale 路径的任务停止使用旧会话，并保留可恢复进度；同一设备仍有经核验的局域网路径时，按连接切换规则继续或重试。
- 首期切换账号通过退出后重新登录完成。旧网络的地址、节点标识和迟到回调不能用于新网络；缓存设备仍可离线浏览，局域网可达设备继续正常使用。
- 清除本机凭据与从官方管理后台删除节点不是同一件事。退出界面不得声称已删除云端设备，除非实际完成且核验该动作；首期不提供管理后台设备删除功能。

## 发现与连接检查顺序

以下顺序已确定，适用于启动、返回前台、网络恢复与用户刷新等需要重新检查设备的场景；具体检查时长和并发数由原型验证后确定：

1. **先检查局域网的已记住设备。** 优先启动 / 恢复 mDNS 发现，核验已记住设备的 LAN 候选地址与 Tamayura 身份，找到可达路径后即可用于同步或下载，不等待互联网或 Tailscale。仍保留通过 LAN 自动发现新设备的既有能力，不把发现范围缩小为仅已记住设备。
2. **再检查本机互联网条件与 Tailscale 注册状态。** 这里的“连接了互联网”指当前运行 Tamayura 的本机，不要求先判断远端设备是否上网。网络条件允许时检查是否已有有效注册身份；未注册、已退出或需要重新认证时保留登录入口，不自动登录，也不阻断 LAN。
3. **已注册后恢复节点，检查是否就绪。** 磁盘上存在旧状态文件不代表就绪；需区分凭据有效、等待设备批准、正在连接、可取得候选状态并尝试连接等实际状态。未就绪时显示对应原因，在网络或节点状态变化时有界重试。
4. **Tailscale 就绪后查询其他设备。** 读取当前节点可见候选，再检查对端 Tamayura 服务是否在线。该发现同时覆盖已记住和新的设备；即使 LAN 已找到部分或全部已记住设备，也继续执行符合条件的 Tailscale 发现，以找出其它远端设备并补充双路径状态。
5. **合并结果并按路径连接。** 同一设备分别保存 LAN / Tailscale 可达状态，新操作优先使用已核验的 LAN，LAN 不可达时使用已核验的 Tailscale。不同设备独立检查与选路，不因为其中一台仅能走 Tailscale 而改变其他设备的 LAN 路径。

“先检查局域网”是启动和检查的优先顺序，不是等连续 mDNS 浏览彻底结束。首轮 LAN 检查使用有界时间，结果可逐步显示；没有 LAN 接口或首轮尚无结果时，条件满足即可进入 Tailscale 检查，不能无限等待，也不能停止后台持续的 LAN 发现。已有仍有效的路径状态可以复用，不要求每次点击下载都重新等待完整发现窗口。

互联网状态由系统网络信息与实际目标服务连接结果共同判断；不以 Google 等账号网站能否访问作为普通组网的前置探针，也不把仅连上 Wi-Fi 等同于互联网可用。系统状态不确定时可进行有界的实际连接检查。上述顺序用于发起 / 恢复发现；短暂失去互联网或管控连接时，不清除注册身份，也不主动拆除仍可达的既有 Tailscale 路径，按实际 RPC 结果更新状态。

## Tailscale 设备发现

技术上有可用的发现基础，但不是把 mDNS 广播直接转发到互联网。`tsnet.Server.LocalClient()` 可访问当前内嵌节点的本地 API，`Status()` 返回该节点已知的 peer 信息；可以订阅 `WatchIPNBus()` 的状态通知，并按所固定版本支持的通知内容更新候选列表。通知结构不保证跨版本稳定，订阅断开后须重新取得快照，不沿用过期事件。无需让用户提供整个 tailnet 的管理 API 令牌。[tsnet 本地客户端](https://pkg.go.dev/tailscale.com/tsnet#Server.LocalClient)、[Status](https://pkg.go.dev/tailscale.com/client/local#Client.Status)、[WatchIPNBus](https://pkg.go.dev/tailscale.com/client/local#Client.WatchIPNBus)

「其他设备」限定为当前 tailnet 中对本节点可见、网络策略允许连接的 Tamayura 对端，不是所有登录过 Tailscale 的互联网设备，也不保证同一 tailnet 的所有成员都相互可见。设备名、MagicDNS 名称或 Tailscale 在线标志都不能单独证明该设备正在运行 Tamayura。

建议采用以下发现流程，待原型验证后确定探测频率和超时：

1. 按上述顺序确认本机网络条件、有效注册与节点就绪后，从本地 API 获取候选节点，排除本机；已建立的节点会话可继续消费状态变化。初次发现、返回前台、状态变更和用户刷新可触发候选更新；合并重复事件并限制并发和频率。
2. 仅对可见候选的 Tamayura 约定服务端口发起有界探测，不扫描整个 `100.64.0.0/10` 地址段，不枚举任意端口。
3. 通过 tsnet 连接后调用现有 `GetIdentity`，核验非空设备身份和协议兼容性。探测成功才作为 Tamayura 设备展示；普通 Tailscale 节点不显示为待确认设备，单次探测失败也不伪造空设备。
4. 核验 Tailscale 节点身份后，以 Tamayura 稳定设备 ID 关联局域网与 Tailscale 的记录，保存各自的地址和可达状态。设备名称、虚拟 IP 或账号名称不能作为设备唯一键；远端绑定同时记录所属网络与 Tailscale 节点关联。首次将 Tailscale 节点绑定到已有 LAN 设备时，不能只凭自报的 `GetIdentity.id` 静默合并信任；无法证明两者关联时先请用户确认，再合并路径。
5. 自动发现的新设备沿用「待确认 → 开始同步 / 暂不同步」流程。登录 Tailscale 不代表自动同意同步整个网络；已建立可信绑定的同一设备新增地址或恢复路径不重复提示。路径关联确认不重置原有相册同步的批准 / 拒绝决定。详见 [新设备确认与忘记设备](新设备确认与忘记设备.md)。
6. 已记住设备仍保留在列表中；离线、策略撤销或候选列表暂时缺失不删除设备及缓存。恢复连接后重新核验身份，再恢复可用路径。

远端节点若与已绑定的 Tamayura ID 冲突，或者同一个地址返回不同身份，应停止该绑定的连接并报告异常，不能覆盖原设备的相册或下载来源。节点重新注册、账号切换产生的新绑定需要重新核验关联，不能仅因旧虚拟 IP 或自报设备 ID 相同沿用旧信任。服务端可在真实 Tailscale 连接入口使用 `LocalClient.WhoIs` 核验节点 / 用户信息；采用本机转发时须在 Go 接入端完成，而不是对 Dart 看到的回环地址做此判断。[WhoIs 示例](https://pkg.go.dev/tailscale.com/tsnet#readme-identifying-callers)

建议在每个内嵌 tsnet 节点的虚拟地址上使用固定 TCP 端口 `50728`。局域网服务仍保留当前动态端口回退；虚拟端口与本机监听端口属于不同网络栈，可由适配层连接起来。虚拟监听失败必须可见，不能静默改用未被发现机制公布的新端口。若该方案验证失败，应明确调整服务发布机制，不能悄悄将需求降为只支持手动输入地址。

Tailscale peer 的 `Online` 表示与管控服务的连接状态，`Active` 表示近期活动；两者都不等于 Tamayura RPC 可达。MagicDNS 只解决名称解析，也不是 Tamayura 服务目录。[PeerStatus](https://pkg.go.dev/tailscale.com/ipn/ipnstate#PeerStatus)

## 设备页面与在线状态

一台 Tamayura 设备只显示一张卡片，分别维护局域网和 Tailscale 路径状态。下表描述服务已核验可达后的展示；正在检查、超时、无访问权限或协议不兼容应保留明确状态，不能全部显示为「设备离线」。

| 局域网服务可达 | Tailscale 服务可达 | 设备卡片的在线标识 |
| --- | --- | --- |
| 是 | 否 / 未登录 | 局域网在线 |
| 否 | 是 | Tailscale 在线 |
| 是 | 是 | 局域网在线、Tailscale 在线 |
| 否 | 否 | 离线；保留缓存与最后成功同步时间 |

「Tailscale 在线」表示经 Tailscale 路径可访问对端 Tamayura 服务，不要求 UDP 直连；DERP 中继可用时也属于在线。必要时在连接详情显示「直连 / 中继 / 路径检查中」，不把中继显示为故障，也不把手机使用 Wi-Fi 等同于已通过局域网访问对端。

已登录但本机 Tailscale 断开时，可以显示「Tailscale 未连接」解释远端路径不可用；局域网在线标识独立保留。管控失联但现有远端 RPC 仍可达时，设置显示管控异常，设备仍可显示 Tailscale 在线。探测结果应有时效性，应用重启或旧会话的迟到结果不能永久维持错误在线状态。

双路径在线时，设备或任务详情同时说明当前实际使用的连接方式。显示与操作遵循无障碍要求，不能只用颜色区分；无需让用户在相册里选择不同网络版本的同一设备。

## 连接选择与任务连续性

新操作优先 LAN 已确定：先按前述顺序查找已记住设备的局域网路径，使用已核验可达的 LAN；连接暂时失败或只有 Tailscale 可达时，再使用已就绪且经核验的 Tailscale 路径。身份不符、协议不兼容或明确访问拒绝不按普通断线无限换路，也不能用另一条路径掩盖身份冲突或绕过明确的授权拒绝。

以下任务连续性行为仍为建议默认值，不能表述为已实现的无缝切换：

- 正在正常传输的任务保持当前路径，不因另一条路径上线而反复迁移。当前路径断开后，在既有重试 / 续传边界重新选择候选，并再次核对设备身份和文件状态。
- 路径切换会重建底层连接，不能承诺保留原 TCP / gRPC 流。复用相册同步断点和下载分片恢复，避免重复任务、重复完整文件及错误应用删除。
- 两条路径共用同一设备的同步确认、尝试时间、最后成功时间、同步间隔及任务互斥。双路径事件不能并发拉取两个目录快照；重复发现和状态通知不能变成持续同步轮询。
- 对上次同步失败设备的上线重试沿用一次性边沿语义；可用路径恢复可触发一次，重复在线通知不能反复绕过同步间隔。具体合并规则须在双路径时序测试中明确。

离线浏览、最后成功同步时间及设备排序继续依据 Tamayura 设备记录，不因切换网络重建。忘记设备继续遵循现有的数据清理边界，且须阻止来自两种发现来源的迟到回调把刚删除的设备立即写回。

## 相册、下载与蜂窝网络

| 操作 | 通过 Tailscale 的目标行为 |
| --- | --- |
| 相册同步 | 沿用自动间隔、手动刷新、分页、断点与完整快照提交；更新元数据和缩略图，不自动下载全部原文件 |
| 离线浏览 | 使用同一份设备、相册与缩略图缓存；退出登录或远端不可达仍可浏览 |
| 点击照片 / 视频 | 通过可用路径下载到现有接收目录；已保存文件与任务复用规则不变 |
| 大文件 | 保留超过 50 MiB 使用四路范围下载的业务行为，验证高延迟与中继场景的内存和吞吐 |
| 暂停、恢复、取消 | 保留分片、可重试保存和历史记录规则；路径切换不删除已接收文件 |
| 错误与恢复 | 区分登录失效、网络不可达、无权访问、协议不兼容、源文件变化与本地保存失败；只能显示实际能判断的原因 |

操作入口和结果应与局域网一致，但不保证速度相同。既有范围读取、文件状态校验、停滞重试和空间边界继续适用，详见 [传输恢复](传输恢复.md)、[下载存储与清理](下载存储与清理.md)、[自动与手动同步](自动与手动同步.md)。

必须支持用户在蜂窝网络上主动同步相册、下载原文件；Android UIDT 调度与后台工作引擎都须能够使用该路径。首次使用时应清楚说明会消耗移动数据，不能仅前台调用成功就宣称已支持后台下载。计费网络上的自动同步、缩略图预取和自动续传是否提供独立开关、默认如何设置，仍待细化；这些待定项不能反过来阻止未登录用户的局域网任务。

沿用已有「后台共享」和桌面托盘生命周期：应用真正退出、系统休眠或平台暂停执行时不承诺远端仍可访问。内嵌用户态组网不等于获得 Android / iOS 无限后台执行权限。[后台共享](后台共享.md)、[桌面托盘与窗口生命周期](桌面托盘与窗口生命周期.md)

## 技术方案与待实现边界

gRPC / HTTP/2 可以运行在 tsnet 的 TCP 连接上，无需因为组网方式改变而重写媒体协议。需要适配的是 Dart 系统 Socket 与 Go 用户态网络栈的连接入口，客户端拨号和服务端监听都要覆盖。

| 方案 | 评估定位 | 必须处理的边界 |
| --- | --- | --- |
| 本机 TCP 透明转发 | 建议优先用于可行性验证；Dart gRPC 接本机转发端，Go 经 tsnet 拨号 / 监听，双向转发原始字节 | 回环入口限制、缓冲与背压、错误和关闭传播、真实对端身份在桥接边界的核验、额外拷贝及实测性能 |
| 原生双向字节流桥接 | 后续按原型结果选择；通过 Dart gRPC / HTTP/2 的连接扩展接口直接使用 Go 连接 | 跨语言异步 I/O、内存生命周期、流控、取消、EOF 与错误处理；不能假设无需适配或性能必然更好 |

### Go 本机桥接组件的职责

本机 TCP 透明转发可以理解为一个由 Tamayura 管理的 Go 子服务：Go 组件持有 tsnet 节点，并在需要 Tailscale 连接时监听本机回环端口；Dart gRPC 客户端连接该端口，经 Go 组件把原始双向字节流转入 / 转出 Tailscale 网络。这是当前优先验证的桥接方向，尚未编写实现。

完整通信需要两端都具备收发入口：

1. **发起端：** Dart 请求桥接组件为指定远端设备准备连接映射；Dart gRPC 连接相应本机回环入口，Go 调用 `tsnet.Dial` 连接远端的 Tailscale 虚拟服务端口。
2. **接收端：** Go 通过 `tsnet.Listen` 接受连接并核验真实对端身份，再转发到同机现有 Dart gRPC 服务的实际监听端口。
3. **响应与流式传输：** 两端持续双向转发；响应、文件分块以及 HTTP/2 控制帧沿相反方向返回，不需要对每个 RPC 创建新的业务协议。每台设备都可以同时是发起端和接收端。

负责监听“给 Dart 客户端使用的本地转发端口”的是 Go 组件。Dart 原有的 gRPC 服务端仍负责相册、文件和共享目录业务；两者的监听端口职责不同，远端 tsnet 虚拟端口也不是本机回环端口。回环转发入口应绑定 `127.0.0.1` 等本机地址，不绑定 `0.0.0.0`。

多设备并发时，必须显式管理“本机入口 → 当前账号下的目标节点 / 虚拟端口”映射，普通 gRPC 字节流不会自动告诉透明转发层应连接哪台设备。可先评估按目标分配动态回环端口，由 Dart 通过受限的本机控制接口取得映射；每条已建立连接固定所属目标与会话，不能使用全局“最后选择的设备”决定转发目标。本机端口不作为远端地址写入设备记忆或二维码，重启后重新建立映射。控制接口与转发入口均须限制本机调用权限，不能因绑定回环就假设其它本机程序无法访问。

Go 组件承接的是连接与原始字节流，不解析相册消息、不重新编码 Protobuf，也不将现有 Dart gRPC 业务重写为 Go。登录、节点状态、发现及映射管理通过独立的受限控制接口或平台调用交给 Dart；不要混入媒体 gRPC 字节流。

“子服务”描述逻辑职责，不限定每个平台必须启动独立进程。Windows、macOS、Linux 可以评估随应用打包的 Go 辅助进程；Android 优先评估原生库在应用进程内运行 Go 组件，同样可以使用本机回环桥接。运行形态仍须平台验证，不能直接把桌面子进程方案当成移动端保证。辅助组件随应用及获准的后台任务管理，不安装开机常驻系统服务。[tsnet 拨号与监听](https://pkg.go.dev/tailscale.com/tsnet)、[进程内 C 库形式](https://github.com/tailscale/libtailscale)

应用启动先恢复 LAN 能力；只有用户发起登录或恢复已有注册身份并需要 Tailscale 能力时，才启动 / 恢复组网组件。不能因为采用“子服务”就要求所有未登录用户在启动时等待 Go 网络节点就绪。

局域网发现、监听和客户端必须能独立工作。Tailscale 路径使用单独候选与连接工厂，不能把所有连接全局改为通过 tsnet，也不能将 Tailscale 初始化失败作为全局网络停止条件。

现有设备模型与下载任务只保存单组地址，在线状态也未按路径拆分；需要新增候选路径、网络归属及可达状态，并让下载重试重新选路。认证状态变化、网络切换和退出登录须使用会话隔离，避免旧异步结果覆盖新状态。Android 前台与后台 Flutter 引擎须协调同一个节点身份和生命周期，不能同时竞争同一状态目录或重复注册节点。

`tsnet` 提供 Go 接口；`libtailscale` 是可评估的 C 封装，不能当作现成 Flutter 全平台 SDK。Windows 封装与 Android 内嵌兼容性仍需原型和真机验证；固定依赖版本后再确定各平台桥接和打包方案。[tsnet](https://pkg.go.dev/tailscale.com/tsnet)、[libtailscale](https://github.com/tailscale/libtailscale)、[Windows 支持跟踪](https://github.com/tailscale/tailscale/issues/7649)、[Android 内嵌跟踪](https://github.com/tailscale/tailscale/issues/17311)

## 安全、数据与兼容要求

- Tailscale 路径的加密与网络访问控制由 WireGuard 和 tailnet 策略提供，首次使用面向已授权的个人设备；登录成功不意味着所有成员均获准读取所有媒体。需核验实际 grants / ACL 对来源、目标和服务端口的限制。[Tailscale grants](https://tailscale.com/docs/features/access-control/grants)
- 「确认同步」控制本机是否同步该对端，不是保护本机分享目录的服务端授权。现有 Tamayura ID 核对也不是密码学认证；Tailscale 对端身份应在内嵌节点边界核验，不能信任任意本地调用方自报的远端身份。
- 保持既有局域网能力不代表将无鉴权监听器开放到公网。内嵌 Tailscale 只保护经过它的流量；原有 LAN 监听、回环桥接与远端监听的边界须分别验证，不自动配置公网端口映射、Funnel、exit node 或 subnet router。
- 新配置和多地址持久化如需数据库迁移，应遵循 [兼容与升级](兼容与升级.md)，保留设置、授权、设备确认、缓存、历史与分片，支持失败回滚；不能通过清空数据库实现接入。
- 纯传输适配不预设必须升级 gRPC v4。若最终需要变更协议，另行进行兼容设计和新旧正式版本测试；旧版设备在局域网内仍按兼容策略互联，不将它们误标为已经支持应用内 Tailscale。
- `tsnet` 使用 BSD 3-Clause 许可证，分发须保留相应声明并核对实际依赖许可；开源客户端不代表官方管控服务开源。[许可证](https://github.com/tailscale/tailscale/blob/main/LICENSE)

## 待实现后的验收清单

下列条目均为未来验收要求，当前未执行。自动化测试与真实网络测试分别记录，不以模拟事件或回环传输替代跨运营商验证。

| 场景 | 必须达到的结果 |
| --- | --- |
| 从未登录 / 官方服务不可达 | 无需账号即可完成既有 LAN 自动发现、手动连接、相册同步与下载；启动不被 Tailscale 阻塞 |
| 发现顺序与条件 | 先检查 LAN 已记住设备；互联网不可用、未注册或未就绪时正确处理；LAN 首轮无结果不无限等待，纯蜂窝可进入 Tailscale；LAN 找到 A 后仍能发现仅 Tailscale 可达的 B，Google 不可达不阻断正常组网 |
| 登录流程 | 浏览器认证、取消、超时、设备审批、认证失效均有正确状态；重启不重复注册 |
| 退出与账号切换 | 停止旧节点连接、阻止旧会话回调和凭据复用；LAN 任务与本地数据保留 |
| 远端发现 | 正确显示可访问的 Tamayura 节点；普通 Tailscale 节点、不可见节点和身份不兼容节点不作为可用设备 |
| 新设备确认 | 发现后先待确认；拒绝后不自动同步；首次路径关联有核验，已绑定双路径不重复提示、不同步两次 |
| 在线标识 | LAN、Tailscale、双路径、离线分别正确；控制在线但 RPC 不通不能标为 Tailscale 在线 |
| 管控连接中断 | 显示真实管控状态；仍可达的既有连接按实际情况保留；不自动注销或影响 LAN |
| 多路径与身份 | 一个设备只出现一次；地址变化不覆盖另一条路径；新网络中相同自报 ID 不静默继承信任；错误设备身份不能接续原任务 |
| 切换与恢复 | 在 LAN / Tailscale 之间断线恢复，保留分页与下载分片；不因切路额外产生重复任务 / 完整文件、错误删除或重复快照提交；保存与数据库登记非原子事务的既有异常边界仍保留 |
| 蜂窝访问 Windows NAS | 手机关闭 Wi-Fi，完成相册、缩略图与原文件传输；后台、锁屏、Wi-Fi / 蜂窝切换另行验证 |
| 直连与中继 | 两种路径均完成同步、小文件及大于 50 MiB 的下载；记录时延、吞吐、停滞和恢复 |
| 访问控制 | 不允许的来源 / 端口无法访问；撤销策略或本机退出后不能继续绕过限制；LAN / 回环入口未意外暴露 |
| 进程与平台生命周期 | 前后台引擎、桌面托盘、应用重启与睡眠恢复不重复节点；各平台按实际支持范围验收 |
| 双向桥接与多目标 | 每端均可发起 / 接受 gRPC；不同设备并发与四路下载不串线；Dart 动态端口正确映射到固定虚拟端口；重启和账号切换不复用旧映射；后台引擎可取得有效桥接，Go 组件失败不阻塞 LAN，回环接口访问控制有效 |
| 版本升级 | 既有数据库和配置安全迁移，旧数据保留；LAN 新旧版本互联满足兼容策略 |
| 界面与错误 | 三语言、窄屏、大字体、加载 / 错误 / 重试状态完整，局域网能力不被登录引导遮挡 |

中国大陆连通性需在实际家庭宽带与手机运营商组合上测试：完成官方认证后关闭辅助登录的代理，保留登录状态并重启客户端，分别检查管控连接、UDP 直连、DERP 可用性及持续传输，包含晚高峰。公开案例不能代替该验收，也不保证认证成功后官方服务持续可达；背景资料见 [互联网访问规划](互联网访问规划.md)。

## 继续细化的事项

以下事项不影响已确定的核心需求与发现 / 连接优先级，也不作为本轮文档工作的阻塞条件：

1. **计费网络策略**：自动同步、缩略图加载及断线后的自动续传，是否单独提供移动数据开关及其默认值；用户主动操作必须支持蜂窝网络。
2. **在途任务与展示**：正常任务不主动迁移的建议、断线切换时机，以及直连 / 中继放在详情还是设备卡片；新操作先 LAN、再按条件检查 Tailscale 的顺序已确定。
3. **发现与集成细节**：首轮 LAN 检查预算、固定虚拟端口、候选探测频率、在线结果有效期、节点重注册绑定、Go 组件运行形态及回环映射接口，由原型确定后补齐；发现能力若有平台限制须单独说明，不能预先标记全部平台已可用。
